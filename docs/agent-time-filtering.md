# Agent 时间检索更新说明

更新日期：2026-10-16。适用于 v0.1.1 之后的本次修复，不改变 API 路径或数据库表结构。

## 修复的问题

此前 Agent 的规则解析器没有覆盖所有自然语言时间表达，系统提示也没有直接提供任务
时间和用户时区。模型可能自行查询当前时间，但把 `time_filter` 对象编码为 JSON 字符串，
触发参数校验错误；随后省略筛选条件，最终把更早的资料作为近期证据。

例如，用户问“最近一周有哪些投资机会”，旧行为可能引用一个月前的报告。修复后，Agent
先确定用户实际要求的时间范围，再执行带约束的检索；范围内没有资料时明确说明证据不足。

## 现在的执行方式

1. 以任务创建时间和用户时区为基准，通过现有 Chat 模型的 JSON 结构化接口解析时间意图。
   时间理解不依赖固定短语列表或固定日期；滚动窗口、日历周期、绝对日期、开放区间及多时期
   比较均由用户原话确定。用户未要求时间筛选时，不强加时间条件。
2. 校验结构化范围，包括时间字段、时区、起止顺序和至少一个有效边界。默认按资料的
   `source_time` 筛选，排除时间未知的资料；用户明确指定时才使用创建或更新时间。
   无法确定的时间请求会报告需要澄清，解析失败不会静默降级为无时间筛选。
3. 将时间计划保存到已有 `AgentRun.state_json.time_plan`，同时把基准时间、时区和解析
   结果注入执行及最终答案整理上下文。自动重试复用同一计划，不随着重试时间移动范围。
4. 后端为知识检索、时间线检索、Wiki 检索和图检索补齐时间条件，并将模型请求限制在
   已解析的范围内。多时期查询必须分别指定独立区间，不能合并成覆盖中间时期的大范围。
   文档和 Wiki 正文读取也检查时间，避免重新引入范围外的证据。
5. 兼容模型传来的 JSON 字符串时间对象，统一工具的时间参数 Schema，并在步骤记录中
   保存实际生效的检索参数。空结果明确说明证据不足，不能把工具步骤编造成来源引用。

首次执行增加一次时间意图解析调用；这一步请求关闭推理，并使用现有结构化输出接口。
解析耗时计入 Agent 每次执行的超时预算。模型仍须具备可用的 JSON 结构化输出能力，
自然语言解析结果也依赖所配置模型的能力。

## 更新部署

在现有 v0.1.1 部署上拉取包含本次修复的代码后，重建并更新 Agent Worker：

```bash
docker compose build agent-runner
docker compose up -d --no-deps agent-runner
docker compose logs --since 5m agent-runner
```

无需新增数据库迁移，也无需修改模型配置或前端。更早版本升级到 v0.1.1 时，仍须先完成
[账号和队列升级流程](upgrading-accounts-and-queues.md)。

已完成的历史回答不会自动重算，需要重新发起问题。该更新针对 Agent 执行链路，普通 RAG
接口的时间解析流程保持原有行为。

## 验证

- 227 项单元测试通过，并通过 Agent 模块的 Ruff 和 mypy 检查。
- 使用实际部署的模型验证了“最近一周”“从上周三到昨天”“上个月最后五天”、跨年比较
  和无时间限定问题。结构化解析在该次验证中的耗时约为 3–8 秒，不代表性能保证。
- 完整重跑近期问题，确认知识检索、时间线和 Wiki 工具均保留时间条件；模型省略时间
  参数时由后端补齐。目标时间范围内没有资料时，任务完成并明确说明证据不足，没有返回
  范围外引用，也没有生成虚构引用编号。
